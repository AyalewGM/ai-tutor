# ADR-013: Stepwise work checking and in-problem intervention

## Status
Accepted. Implemented on `feature/f-026-math-notation-scratch-pad` (PR #128). The escalation thresholds are a provisional `pilot-v1`-style policy pending owner research, mirroring the ADR-010 pattern of versioned, replaceable hypotheses.

## Context
Pre-stepwise adaptivity operated only *between* problems: an attempt was graded as a whole, and the next problem was selected from that evidence. This cannot detect *where* in a solution a learner went wrong, and a learner who made a recognizable error mid-solution but recovered produced no misconception evidence at all. Competing products (IXL and beyond) adapt *inside* a problem. The gap decomposes into: (1) gradeable intermediate representations per problem family, (2) an intervention policy, (3) a UI that is honest about what can actually be verified.

## Decision
1. **A work line is a mathematical state, not a solution step.** For equations, a submitted line is legal iff it preserves the solution set of the previous line — normalized polynomial coefficients proportional in exact `Fraction` arithmetic. This deliberately permits multiple valid routes (distribute-first vs. divide-first) rather than enforcing one canonical path.
2. **Expression families use value equality plus a simplified-form check.** A line is a valid step iff its value equals the previous line's; it is the final answer only if also fully simplified (no expandable parens, ≤1 term per degree, lone fractions in lowest terms — `10/12` is a valid step but not the answer).
3. **Parsing is deterministic and narrow, with a bounded SymPy fallback.** The primary parser is a small recursive-descent parser for integer/fraction coefficients, implicit multiplication (`3x`, `2(x+4)`), division (`x/2`), and signed terms. When it cannot read a line, a bounded SymPy path parses with `implicit_multiplication_application` + `convert_xor` and then **converts the result back to the native polynomial representation** — univariate, nonnegative-integer exponents, ≤80 nodes, ≤120 chars, no function calls. The fallback only widens *syntax* (`x^2`, `x**2`, nested forms, decimals); semantics (equivalence, solved-form, classification) are identical on both paths and no `simplify`/`equals`/`solve` runs on the request path. Non-polynomial forms (rational expressions, `sin(x)`, multi-variable input) stay honestly unparseable.
4. **Step checking is only offered where it is honest.** `supports_steps` requires `answer_kind == "FREE_TEXT"`, a supported `problem_type`, and a prompt the parser can decompose. Multiple-choice variants of the same `problem_type` are excluded.
5. **Supported families:** `SOLVE_EQUATION`, `SIMPLIFY_EXPRESSION`, `COMBINE_LIKE_TERMS`, `FRACTION_OPERATIONS`, `FRACTION_SUBTRACT`, `WORD_PROBLEM`, `ALGEBRA_WORD_PROBLEM`. Numeric word problems (`WORD_PROBLEM`) use a *model→compute* check rather than equation equivalence: the first line is the learner's model calculation, which must evaluate to the canonical numeric answer (catches wrong setups deterministically); later lines must preserve that value; a bare correct answer at any point is solved. A numerically-right-but-semantically-wrong model (`60/5` for "20% of 60") passes — a documented honesty boundary, since semantic model-checking needs the LLM layer and is deferred. Trailing unit words (`12 dollars`) are stripped for value comparison. `ALGEBRA_WORD_PROBLEM` adds a **declare→setup→solve** state machine reconstructed server-side from accepted lines: `x = miles driven` declarations are format-checked (a two-plus-letter description; `x = 12` or `x = y` stay equations, not declarations); the setup equation must use the declared variable, parse as linear, and have `_solution_value == canonical` — a wrong model is `WP_001`, deterministically caught without understanding the prose; solve lines then ride the ordinary equation equivalence checker. Reveals are possible only in the SOLVE phase — a model can't be honestly revealed — so earlier phases cap at targeted feedback. A correct final answer (`x = 8`, bare `8`) still solves at any point.
6. **Misconception classification fires on transitions, not states.** Recognizable wrong *transitions* map to catalog codes. Equations: `3x+12=30 → 3x=42` → EQ_001 (wrong-direction move), `3(x+4)=30 → x+4=30` → EQ_002 (one-sided operation), `3x+12=30 → 15x=30` → ALG_001 (unlike terms merged), `3x-5=16 → 3x+5=16` → ALG_002 (constant sign dropped), `3x=18 → x=54` → EQ_003 (multiplied by the coefficient — integer |k|>1 only, so fraction-coefficient confusions aren't mislabeled), `3x=18 → x=15` → EQ_004 (coefficient treated as addend), `3x+12=30 → 3x=20` → ARITH_001 (right move, wrong value — constant removed cleanly but the other side recomputed wrong). Expressions: `3(x+4) → 3x+4` → DIST_001 (partial distribution), `3(x-4) → 3x+12` → DIST_002 (distributed with sign flip), `2x+3 → 5x` → ALG_001, `1/2+1/3 → 2/5` → NUM_003 (added across), `2/3+1/6 → 3/6` → FRAC_001 (common denominator, numerators unscaled). Specific patterns run before generic ones (merge/sign-flip before EQ_002's one-side check) so the most precise code wins; unrecognized wrong lines stay invalid but unclassified — no code is asserted when the transition is ambiguous.
7. **Intervention is immediate but graduated, and server-derived.** Invalid-line count is computed from persisted `WORK_STEP` tutor turns — the client cannot fabricate it. `pilot-v1` escalation: 1st invalid → generic retry; 2nd → targeted misconception feedback when classified; 3rd → reveal one legal next line computed from the learner's *current* state (`_canonical_next_line` works from any position). The policy boundary is one function so research can retune it without touching the checker or UI.
8. **Step evidence joins existing evidence flow, not a parallel system.** Work lines persist in `TutorTurn.metadata_json` (no new tables). Step errors raise the effective `assistance_level` used by `respond`, so a solved-by-steps answer is graded honestly as assisted (reduced XP, not independent mastery evidence). The latest classified step error is fed to `record_evidence` as a *fallback* misconception when the final answer carries none, at reduced confidence — closing the recovered-answer blind spot without letting step evidence dominate. Parents see the evidence two ways: `step_trails` (recent worked problems with per-line status) and `recent_patterns` (top-3 misconception codes over 7 days, aggregated from `Attempt.misconception_id` plus WORK_STEP transition codes — counts only, no raw text scan).
8a. **Step evidence drives the tutor voice (F-032).** `TutorContext.step_evidence` carries the learner's latest wrong line, the accepted line it followed, the classifier code, and the invalid streak — reconstructed from `WORK_STEP` turns by `latest_step_evidence` and cleared once a later line is accepted (the voice must not dwell on a corrected error). Hint level 1 stays a nudge; from level 2, and for `EXPLAIN_CONCEPT`, the deterministic fallback quotes the line and names the move from per-code templates. The gateway receives only a compact textual description and is instructed to refer to the line without re-grading it or exceeding the hint constraint — the LLM still renders language over an application-made classification.
9. **UI separates rough work from checked work.** The scratch pad remains freeform and ungraded; `StepWork` renders accepted/rejected lines, misconception feedback, and reveals. Reaching solved form (`x = 6`, `5/6`) auto-submits through the normal `respond` path so XP, awards, and celebrations flow unchanged.
10. **MathText renders KaTeX to DOM nodes via `katex.render`** — no `dangerouslySetInnerHTML` anywhere; learner-typed lines cannot become an XSS sink.

## API
`POST /api/v1/adaptive-tutor/sessions/{session_id}/work-step` with `{problem_id, line}` returns `{status: valid|invalid|solved|unparseable, normalized_line, feedback, revealed_line?, misconception_code?}`. Problem payloads expose `problem_type` and `supports_steps`.

## Consequences
### Positive
- In-problem struggle becomes auditable evidence feeding the same remediation loop as answer-level evidence.
- Multiple solution routes accepted; checker semantics match how math is actually worked.
- No new tables; step trails are already queryable for future parent-facing "where they stumbled" reporting.
- The provisional policy is isolated and versionable.

### Tradeoffs / deferred
- Single-variable polynomials only; rational expressions and systems remain uncheckable. Factoring a quadratic is accepted as a valid step (solution set preserved), but `x = 2` alone after `x² = 4` is correctly invalid — partial roots drop solutions.
- Word-problem models are checked by value only; semantic setup verification (is `x` really "number of tickets"?) is deferred to a constrained LLM role or richer schemas. `ALGEBRA_WORD_PROBLEM` checks the *form* of declarations and the *solution* of the setup equation — not that the prose description is accurate, nor that the setup uses the "intended" numbers.
- Algebraic word problems are limited to linear setups (`_solution_value` rejects anything needing quadratics); multi-unknown systems remain out of scope.
- Escalation thresholds are hypotheses pending pedagogical research and pilot telemetry.
- Expression "fully simplified" is a heuristic for the v1 families, not a general canonical-form proof.

## QA requirements
- Same previous line + same new line ⇒ identical verdict, and equivalent rewrites of a legal step (`3x+12=30` vs `30=3x+12`) are both valid.
- `x = const` / fully-simplified-expression / bare-canonical-word-answer are the only solved forms.
- Invalid count is server-derived; a client-supplied count cannot change escalation.
- Step-mode problems keep MC and non-step families on the classic answer path; `supports_steps` requires the seed (or word-problem canonical answer) to actually parse.
- A solved line's auto-submit produces the same `respond` outcome as typing the answer directly.
- The SymPy path rejects functions, multi-variable input, non-integer exponents, and oversize expressions.
